PREDICCIÓN 1

¿Cuántas formas distintas existen de insertar JavaScript en un HTML?

Confianza:
Respuesta: hay tres formas principales: inline (atributos como onclick), interna (etiqueta <script> dentro del HTML) y externa (<script src="archivo.js">). Además hay variantes con defer, async y type="module".
PREDICCIÓN 2

¿Dónde se recomienda colocar la etiqueta <script src="app.js"> si NO usas defer ni async?

Confianza:
Respuesta: al final del <body>. Si lo pones en el <head> sin atributos, el navegador descarga y ejecuta el script ANTES de parsear el resto del HTML, bloqueando la página (el usuario ve pantalla en blanco hasta que termina).
PREDICCIÓN 3

¿Qué diferencia hay entre defer y async?

Confianza:
Respuesta: ambos descargan el script en paralelo mientras se parsea el HTML. La diferencia es cuándo se ejecuta:
• defer → después de terminar de parsear el HTML, en orden de aparición.
• async → en cuanto esté descargado, interrumpiendo el parsing. El orden no está garantizado.

1 Fundamentos: cómo el navegador carga tu página

Antes de ver cómo insertar JS, necesitas entender qué hace el navegador al abrir un HTML.

El pipeline del navegador

  1. Descarga el HTML desde el servidor.
  2. Parsea el HTML línea por línea, construyendo el DOM (Document Object Model).
  3. Cuando encuentra CSS, lo descarga (en paralelo) y construye el CSSOM.
  4. Cuando encuentra <script>, pausa el parsing, descarga y ejecuta el JS, y luego continúa.
  5. Combina DOM + CSSOM → pinta la página.
🔑 Concepto clave: el DOM El DOM es la representación en memoria de tu HTML como un árbol de objetos. JavaScript no modifica el archivo HTML en disco: modifica el DOM. Por eso puedes cambiar contenido sin recargar.

El DOM visualmente

Cuando tu JS dice document.getElementById("miId"), está buscando un nodo en ese árbol. Por eso el elemento debe existir en el DOM antes de que tu script lo intente usar.

¿Qué es JavaScript?

Es el lenguaje de programación del navegador. Con él puedes:

  • Reaccionar a eventos (clics, teclas, scroll).
  • Modificar el DOM (crear, borrar, cambiar elementos).
  • Hacer peticiones de red (fetch, XMLHttpRequest).
  • Guardar datos localmente (localStorage, IndexedDB).
  • Y un largo etcétera.
⚠️ Antes de continuar Ten presente esta regla mental: "el HTML construye la estructura, el CSS la viste, y JavaScript le da vida". Los tres viven en el navegador, pero se cargan y ejecutan de forma distinta.
AUTOEXPLICACIÓN

Con tus palabras: ¿por qué crees que el navegador pausa el parsing cuando encuentra un <script> sin atributos? ¿Qué problema intenta evitar?

Porque el script puede contener instrucciones como document.getElementById("miBoton").style.color = "red". Si el elemento aún no existe en el DOM, esa instrucción fallaría. Pausar garantiza que el script se ejecuta cuando el HTML ya fue parseado hasta ese punto. El coste: si el script tarda en descargarse, la página queda en blanco mientras tanto.

2 🟠 Forma 1: JavaScript inline

El código se coloca dentro de un atributo HTML, como onclick, onmouseover, onload, etc.

Ejemplo: el botón clásico

<button onclick="alert('¡Hola!' )">Púlsame</button>

⚡ Prueba real (es un botón inline de verdad)

El código que acabas de ejecutar está en el atributo onclick del botón.

¿Cuándo usarlo?

Casi nunca en producción. Solo tiene sentido para:

  • Pruebas muy rápidas de un comportamiento.
  • Ejemplos aislados en documentación o tutoriales.

Ventajas

  • ✅ Se ve inmediatamente qué pasa al pulsar.
  • ✅ Funciona sin archivos adicionales.
  • ✅ Cero configuración.

Desventajas (son muchas)

  • ❌ Mezcla HTML con lógica → difícil de mantener.
  • ❌ No se reutiliza: cada botón necesita su propio código.
  • ❌ No se cachea: se descarga de nuevo cada vez.
  • ❌ Bloqueado por CSP (Content Security Policy) en muchas webs modernas.
  • ❌ No admite import/export ni módulos ES.
  • ❌ Errores de sintaxis son más difíciles de detectar.
  • ❌ Difícil de testear automáticamente.
🚨 Mala práctica 
<button onclick="if (confirm('¿Seguro?')) { document.getElementById('caja').style.display = 'none'; localStorage.setItem('oculto', '1'); }">Ocultar</button>
Este tipo de "inline gigante" es un infierno de mantener. En cambio: 
<button id="ocultarBtn">Ocultar</button>
<script>
  document.getElementById('ocultarBtn').addEventListener('click', () => {
    if (confirm('¿Seguro?')) {
      document.getElementById('caja').style.display = 'none';
      localStorage.setItem('oculto', '1');
    }
  });
</script>
REFLEXIÓN

¿Por qué crees que los frameworks modernos (React, Vue) están en contra del inline?

Porque rompen la separación de responsabilidades (HTML estructural vs lógica) y hacen imposible razonar sobre el flujo de la aplicación. Además, el inline no se puede testear, no se puede compilar, no se cachea y la CSP lo bloquea. Los frameworks prefieren event delegation y manejadores declarativos.

3 🟢 Forma 2: JavaScript interno

El código se coloca dentro de una etiqueta <script> en el propio archivo HTML. Puede ir en el <head> o en el <body>.

Ejemplo: un contador simple

<div id="contador">Contador: 0</div>
<button id="sumarBtn">+1</button>

<script>
  let cuenta = 0;
  document.getElementById('sumarBtn').addEventListener('click', () => {
    cuenta++;
    document.getElementById('contador').textContent = `Contador: ${cuenta}`;
  });
</script>

⚡ Prueba real (script interno)

Contador: 0

¿Dónde colocarlo? Head vs Body

UbicaciónComportamientoRecomendación
<head> Se ejecuta ANTES de que el <body> exista. document.getElementById() devuelve null si busca algo del body. ❌ Evitar (salvo con defer o DOMContentLoaded)
Final del <body> Se ejecuta DESPUÉS de que todo el HTML esté parseado. Todos los elementos existen. ✅ Recomendado
⚠️ Error clásico 
<head>
  <script>
    document.getElementById('miBoton').addEventListener(...);
    // ❌ TypeError: Cannot read properties of null
    // (el body aún no existe cuando esto se ejecuta)
  </script>
</head>
<body>
  <button id="miBoton">...</button>
</body>

Ventajas

  • ✅ Todo en un archivo: fácil de compartir y transportar.
  • ✅ Bueno para páginas pequeñas o prototipos.
  • ✅ No hay peticiones adicionales.
  • ✅ Fácil de leer si el código es corto.

Desventajas

  • ❌ No se reutiliza entre páginas: si tienes 20 HTMLs, copias 20 veces el script.
  • ❌ No se cachea: cada página lo descarga de nuevo.
  • ❌ Mezcla contenido y comportamiento en el mismo archivo.
  • ❌ Archivos HTML gigantes si el JS crece.
  • ❌ Dificulta el trabajo en equipo.
PREDICCIÓN

¿Qué pasa si pones un <script> en el <head> que intenta acceder a un elemento del <body> con document.getElementById()?

Devuelve null porque el elemento aún no existe en el DOM. Si luego haces .addEventListener() o .style, obtienes un TypeError: Cannot read properties of null. Soluciones: mover el script al final del body, usar defer, o envolverlo en document.addEventListener('DOMContentLoaded', ...).

4 🔵 Forma 3: JavaScript externo

El código vive en un archivo .js separado y se enlaza desde el HTML con el atributo src.

Estructura típica

📁 mi-proyecto/
├── index.html
├── styles.css
└── app.js     ← el script externo
<!-- index.html -->
<body>
  <h1>Mi web</h1>
  <button id="saludar">Saludar</button>

  <script src="app.js"></script>
</body>

// app.js
document.getElementById('saludar').addEventListener('click', () => {
  alert('¡Hola desde un archivo externo!');
});
🚨 Error muy común 
<!-- ❌ MAL: el contenido se IGNORA -->
<script src="app.js">
  alert("Esto nunca se ejecutará");
</script>
Si usas src, la etiqueta debe ir vacía. Solo se ejecuta el archivo externo; el contenido interior se descarta.

Los tres atributos clave: src, defer, async

AtributoDescargaEjecuciónOrden
ninguno Bloquea el parsing Al terminar de descargar Sí, en orden de aparición
defer En paralelo Después de parsear el HTML Sí, en orden
async En paralelo En cuanto esté listo No garantizado

Regla práctica: usa defer casi siempre. Reserva async para scripts independientes (analytics, publicidad, widgets) donde el orden no importa.

Ventajas

  • ✅ Reutilizable: un archivo para todas las páginas.
  • ✅ Cacheable: el navegador lo descarga una vez y lo reutiliza.
  • ✅ Separación de responsabilidades: HTML, CSS y JS en archivos separados.
  • ✅ Fácil de testear y de trabajar en equipo.
  • ✅ Admite import/export y type="module".
  • ✅ El editor te da mejor autocompletado y linting.

Desventajas

  • ❌ Requiere un servidor (no funciona abriendo el HTML con file:// en algunos casos).
  • ❌ Una petición HTTP extra la primera vez (amortiguada por caché).
  • ❌ Puede fallar por rutas incorrectas (404).
  • ❌ CORS si el archivo está en otro dominio.
💡 Buena práctica moderna 
<script src="app.js" defer></script>
Lo pones en el <head> con defer: se descarga en paralelo, se ejecuta en orden al terminar el HTML, y el usuario no espera.

Conclusión

  • Si pones el script en <head> sin atributos → el navegador se congela mientras descarga y ejecuta.
  • Si lo pones al final del <body> → el usuario ve la página antes de que el JS se ejecute.
  • defer → descarga en paralelo, ejecuta al final del parsing, respeta orden.
  • async → descarga en paralelo, ejecuta cuando está listo, puede interrumpir el HTML y no respeta orden.
🏆 Regla de oro 
<head>
  <script src="app.js" defer></script>
</head>
Descarga en paralelo y ejecuta cuando el DOM está listo. Es la opción más segura para la mayoría de los casos.

8 🔍 Análisis de errores típicos

Detectar errores en código ajeno es una de las técnicas más potentes para construir un modelo mental robusto. Lee cada caso e identifica el bug antes de revelar la respuesta.

BUG 1 
<script src="app.js">
  console.log("Nunca aparecerá en la consola");
</script>

¿Qué está mal y por qué?

Bug: cuando un <script> tiene src, el contenido entre las etiquetas se ignora. Solo se carga y ejecuta el archivo externo. Si quieres ejecutar código inline, usa una etiqueta sin src.
BUG 2 
<head>
  <script>
    document.getElementById("titulo").textContent = "Hola";
  </script>
</head>
<body>
  <h1 id="titulo">Original</h1>
</body>

¿Por qué falla y cómo se arregla?

Bug: document.getElementById("titulo") devuelve null porque el <h1> aún no existe en el DOM cuando el script se ejecuta (está en el <head>). Al intentar .textContent sobre null, lanza TypeError.
Fix A: mover el script al final del <body>.
Fix B: añadir defer si es externo.
Fix C: envolver en document.addEventListener('DOMContentLoaded', ...).
BUG 3 
<script src="utils.js" async></script>
<script src="app.js" async></script>

// app.js usa funciones definidas en utils.js

Este código puede fallar de forma intermitente. ¿Por qué?

Bug: con async, el orden de ejecución no está garantizado. Si app.js se descarga antes que utils.js, se ejecutará primero y fallará al intentar usar funciones que aún no existen. Es un bug intermitente (race condition).
Fix: usar defer en ambos, o consolidar en un solo archivo, o usar type="module" (que siempre respeta el orden).
BUG 4 
<button onclick="saludar()">Hola</button>
<script src="saludo.js" defer></script>

El botón no hace nada al pulsarlo. ¿Qué puede estar pasando?

Posibles causas:
1) saludo.js no define la función saludar en el scope global.
2) La ruta del archivo está mal (404 en la pestaña Network).
3) saludo.js define saludar dentro de un módulo o IIFE, por lo que no es global.
4) Hay un error previo en otro script que detuvo la ejecución.

Solución profesional: en lugar de onclick, usar addEventListener desde el propio JS. Así puedes tener la función en cualquier scope.
